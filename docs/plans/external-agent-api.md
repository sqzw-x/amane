# 面向外部智能体的接口方案

> 状态: 待实施. 实施完成后按主题并入 `docs/dev/`, 本文随之删除.
> 术语按 [terms.md](../dev/terms.md): 助理指内置智能体, 智能体指用户自己的外部工具, 工具组指 `Capability`.

## 目标

让用户用自己的智能体工具 ([CC]、Codex 等) 管理 Amane 实例. 接入方式是**给出一个地址**: 用户把实例的引导地址粘给智能体, 其余由智能体自行完成. 交付物是引导端点、CLI 与配套的 Skill; 服务端只增加一层派发接口, 不新增领域逻辑.

非目标: 把内部助理换成外部智能体; 让外部智能体参与对话通道; 替代 REST 前端契约.

## 结论

| 决策 | 选择 | 理由 |
|------|------|------|
| 接口形态 | HTTP 派发端点 + CLI + Skill | 端点即接口, CLI 是薄客户端, 无需维持会话状态 |
| 接口来源 | 直接复用助理工具层 | 一处定义, 两处消费; 不重复实现写语义 |
| 服务端新增 | 引导端点 + 目录端点 + 派发端点 | 无领域逻辑; 读面缺口交给指引, 见「能力边界」 |
| 鉴权 | 维持单一 token; 仅引导端点免鉴权 | 引导端点只回固定文本, 不含任何实例数据 |
| 审批 | 软约束: 工具描述 + Skill 礼仪 | 服务端不设闸门, 见「审批」 |
| CLI 定位 | 薄客户端, 非接口本身 | 端点即可用; CLI 只解决 token 保管、入参组装、轮询折叠、自检 |
| CLI 实现 | Go, 单一静态二进制 | 不依赖用户本机运行时; 一个 job 交叉编译全平台 |
| CLI 分发 | GitHub Releases, 智能体自行下载 | 与实例解耦, 桌面与镜像都不必携带; 见「分发」 |

## 能力边界

只封装**本项目的独有语义**, 其余交给智能体自身的能力与指引. 外部智能体有 shell、有文件系统、能读源码, 也能直接操作 SQLite 文件; 为它复刻这些通用能力是浪费, 而且做不全.

据此确定三类处理:

| 类别 | 处理 |
|------|------|
| 领域写语义 (改元数据、合并分类、入队任务) | 做成工具. 这些规则只存在于本项目, 外部无法自行推导 |
| 只读 SQL 与查询预设 | 复用已有工具. 智能体本可直接读库文件, 但沙箱、交付与预设是项目语义 |
| 通用能力 (读日志、看配置、翻文件、跑脚本) | **不做接口**, 只给指引: 路径、环境变量、文件格式 |

指引由实例自身生成, 不写死在文档里: 目录端点附带一份运行时事实 (数据目录、日志目录、DB 文件、配置文件路径, 以及决定它们的环境变量名), Skill 的自服务章节直接取自该块. 路径随版本变化时指引自动跟上, 不需要维护第二份副本.

推论: 本期**不新增任何读端点**. 任务日志由智能体直接读日志目录; 远端实例无法访问服务端文件系统时, 用已有的记录导出端点取整包.

## 为什么不选 MCP

MCP 的价值是有状态会话, 但本场景需要的状态全部在服务端: 查询预设 id、任务 id、结果缓存都可跨请求重建. 客户端唯一会持有的「刚才那条查询的 id」只是一个整数, 由 CLI 输出即可. 反之, MCP 要为每个客户端做配置, 且工具清单在每次会话中占据上下文.

CLI 更适合本场景的另一点: 目标用户已经在用带 shell 的智能体, Skill 机制足以把用法喂给模型.

保留余地: 若将来需要 MCP, 它只是目录端点与派发端点的另一种传输映射 (`tools/list` / `tools/call`), 不影响本文其它设计.

## 复用边界

### 现状

助理的工具层是 44 个工具, 分布在 7 个工具组与 1 个探查工具集, 覆盖番号条目、演员、分类、媒体库、订阅源、定时任务、任务队列的写操作, 以及只读 SQL 探查与查询预设交付. 工具的返回值、审批闸门、入参校验与错误文案都已在工具层定形.

REST 层不是同一形状: 资源式端点、没有工具描述与派发审计、无 SQL 通道. 再写一层 REST 封装等于把工具层的语义复制一遍, 两边会漂移.

### 取用方式

服务端不重写工具, 而是遍历工具组取得工具定义, 按名字派发:

- 目录: 对每个工具组取工具集, 逐条读出工具名、描述、参数 JSON Schema 与返回 Schema.
- 调用: 先用工具自带的校验器校验入参, 再以派发上下文调用工具函数本体.
- 上下文: 工具函数只读取运行上下文的三个属性 (依赖、`tool_call_id`、`tool_call_approved`), 因此用一个最小上下文对象代替框架的运行上下文即可. 该做法已被现有测试采用, 实现时把该对象从测试挪进包内共用.

验证结论: 上述取用方式在 `pydantic-ai` 当前版本上可直接运行, 44 个工具名无冲突, 参数 Schema 完整, 破坏性工具在「已批准」上下文中可正常执行. 目录与派发依赖的框架面 (工具组取工具集、函数 Schema 的校验器与调用入口) 集中在一个适配模块内, 并以全量目录测试兜底: 框架升级破坏取用方式时该测试直接失败, 不会静默降级.

### 两处必要改动

1. **会话归属**: 外部调用没有对话会话, 交付的查询预设必须与会话解耦. 依赖里的会话 id 改为可空, 交付时按「无会话」写入并标记为已保留, 于是预设进入预设列表而不是随会话清理. 探查视图仍按未保留写入, 只按 id 取行, 不进列表.
2. **不依赖模型配置**: 目录从工具组构造, 不经由助理工厂, 因此未配置模型时外部接口照常可用.

审批不需要改动: 派发层始终以「已批准」的上下文调用, 工具层的闸门因此只对内置助理生效, 外部通道不出现审批分支, 见「审批」.

## 服务端契约

### 引导端点

`GET /public/agent`

**免鉴权**. 返回一份固定的接入指引, 让一个刚拿到实例地址的智能体知道接下来该做什么.

它是整个方案里唯一公开的端点, 因此规则很硬:

| 约束 | 原因 |
|------|------|
| 只回固定文本 | 不拼接实例地址、版本、路径、token、用户名. 任何人都能访问, 任何注入都是泄露面 |
| 不读配置、不查库 | 除常量外没有输入, 也就没有可被利用的差异 |
| 不写访问日志的入参 | 路径固定, 没有 query, 不需要为它记额外字段 |

实例地址由调用方自己知道 —— 它就是用户粘给智能体的那个 URL, 因此指引里写「本文档的 origin 即实例地址」, 而不是把地址嵌进响应.

正文草案 (实现时以它为准, 只允许措辞调整):

```
# 接入 Amane

你在帮用户通过命令行管理一个 Amane 实例 (媒体元数据管理服务).
实例地址 = 你获取本文档所用 URL 的 origin, 例如 http://127.0.0.1:8000.

按两个阶段进行. 每个阶段动手前先向用户说明, 并按下面要求征求同意.

## 阶段一: 安装 CLI

1. 判断本机平台 (darwin / linux / windows, amd64 / arm64).
   从 GitHub Releases 下载对应产物并校验 SHA256SUMS:
   https://github.com/sqzw-x/amane/releases/latest/download/amane-{os}-{arch}
   用 curl 下载, 不要用浏览器打开链接 (macOS 会给下载物加隔离属性, 导致无法运行).

2. 安装位置要问用户, 不要自己决定. 建议 ~/.local/bin/amane
   (Windows 为 %LOCALAPPDATA%\Amane\bin\amane.exe), 并告知:
   装到已有 PATH 目录则装完可直接调用; 否则之后都用绝对路径调用.
   需要修改 PATH 时, 先给出要追加的那一行, 经用户同意后再写, 不要擅自改 shell 配置.

3. 鉴权. 分两种情况, 先判断再决定是否打断用户:
   - 本机就是运行实例的机器: CLI 会自动读取实例数据目录里的 token, 用户无需操作.
   - 否则需要用户手动登录一次: 运行 `amane login --server <实例地址>`,
     CLI 会提示用户粘贴 token (token 在实例 Web 界面的「连接智能体」页可复制).
     让用户自己粘贴. 不要向用户索要 token 后代为输入, 也不要读取或回显它.

4. 运行 `amane doctor`. 全部通过才算阶段一完成; 有失败项就把输出原样交给用户.

## 阶段二: 安装 Skill

5. 运行 `amane skill install`. 它会写入 Skill 目录; 先问用户装到哪个目录,
   不确定就停下来问, 不要猜, 也不要往系统目录写.

6. 安装完成后读一遍完整说明. 此后所有操作都通过 CLI 完成.

## 约束

- 不要自己拼 HTTP 请求调用接口, 一律经由 CLI.
- 不要在对话里回显 token, 也不要写入任何文件或命令历史.
- 删除、合并、批量修改这类操作, 执行前先向用户复述影响面并取得明确同意.
- 需要查日志、配置或数据库时, 按 Skill 里的路径直接读文件, 不要为此调用接口.
```

**实现注意**: 路由必须注册在 SPA catch-all 之前, 并把 `/public/` 加进 SPA 的保留前缀, 否则未命中时会被前端 fallback 接走.

### 目录

`GET /api/tools`

```json
{
  "version": "0.22.1",
  "schema": "表与连接键的文本摘要",
  "paths": {
    "data_dir": "/data",
    "log_dir": "/data/logs",
    "db_path": "/data/amane.db",
    "config_path": "/data/config.toml",
    "env": ["AMANE_DATA_DIR", "AMANE_LOG_DIR", "AMANE_TOKEN"]
  },
  "tools": [
    {
      "name": "update_metadata",
      "group": "metadata-ops",
      "description": "…",
      "params": { "type": "object", "properties": {}, "required": [] },
      "returns": {}
    }
  ]
}
```

该端点同时是说明书: `schema`、`paths` 与工具描述合起来足够一个陌生智能体开工, CLI 的 `--help`、Skill 的参考页与自服务章节都由它生成, 不另存副本.

### 派发

`POST /api/tools/{name}`

```json
{ "args": { "…": "…" } }
```

响应语义:

| 状态 | 含义 |
|------|------|
| 200 | 工具执行完毕. 响应体是工具返回值原样: `"OK"`、对象, 或带 `error` 键的对象 |
| 404 | 工具名不存在 |
| 422 | 入参未通过校验, 回字段路径与原因 |
| 500 | 未预期异常, 只回通用文案, 细节进日志 |

工具级的 `error` 保持 200: 它是工具结果而不是传输失败, 与助理看到的形态一致, 也避免智能体把「参数不对」误判为接口故障.

### 审批

**外部派发不设审批闸门**. 工具层的闸门是为内置助理服务的 (界面会真的中断回合等用户点击), 外部通道没有这个界面, 因此派发层直接以「已批准」的上下文执行工具, 请求里**不携带**任何批准字段.

理由: 在单 token 信任模型下, 客户端自带一个布尔字段不构成约束 —— 它既不能证明用户同意过, 也不能阻止智能体自行置真, 只会让人误以为有保护. 与其留下一个看起来像闸门的东西, 不如明确承认外部通道没有闸门.

破坏性操作的约束改由两层软约束承担:

1. **工具描述**: 目录里的描述是智能体判断风险的一手依据. 现有描述已说明动作与对象, 但影响面不齐 (例如删除媒体库未说明磁盘上的文件是否保留, 删除番号条目未说明关联记录如何处理). 实施时统一补一句: 作用范围 (单条 / 批量 / 级联到哪些记录) 与可否撤销.
2. **Skill 的审批礼仪**: 逐项列出必须先取得用户明确同意的操作 (删除、合并、批量修改、放宽超时执行慢查询), 并要求先复述影响面、得到答复后才执行.

软约束的可靠性依赖智能体遵守 Skill; 服务端不校验. 能兜底的是审计日志, 见下节.

**硬约束 (本期不做)**: 若要真正拦住, 批准必须由人类在智能体够不到的通道上完成. 做法是工具调用需要批准时, 派发层登记一条待批记录 (带过期时间) 并返回一个审批页 URL; 用户在浏览器打开该页, 看到预览并点击确认 (浏览器 cookie 与 Bearer 是两条通道, 智能体没有 cookie); CLI 在超时内轮询该记录的状态, 批准后继续执行, 拒绝或超时则返回未执行. 它需要一张待批表、一个页面、一个轮询端点与阻塞等待, 与本文「无状态」的前提相反, 因此单独立项.

### 审计

每次派发写一条结构化日志: 工具名、结果类别、入参摘要、请求 id. 该日志同时进入日志页, 于是界面能看到外部智能体做了什么. 在没有闸门的前提下, 这是唯一的事后手段, 也是「谁改了什么」的答案.

## CLI

### 定位: 薄客户端, 不是接口

**接口是派发端点**, CLI 只是它的一种调用方式. 智能体完全可以直接 `curl`, Skill 把两种调用式并列给出. 因此 CLI 存在的理由必须是具体的、可验证的, 否则它就是一层需要维护的重复物.

它只承担四件事, 这四件事都是「让模型自己拼 curl」做不好或做不了的:

| 职责 | 为什么模型自己做不到 |
|------|---------------------|
| **保管 token** | 裸 curl 要么把 token 写进命令行 (进 shell 历史与 `ps`), 要么依赖调用方环境里已有的变量 (智能体环境常常没有, 且任何 `env` 转储都会泄露). CLI 自己从 0600 文件读, **token 从不进入模型上下文** |
| **组装入参** | 复杂入参是嵌套 JSON. 内联进 shell 要跨两层引号, 是模型最容易出错的地方; CLI 接受 `@文件`, 由调用方写文件, 不经 shell 解析 |
| **折叠轮询** | 等任务终态是「查询 → 睡 → 再查」的循环, 每次循环都是一次模型回合. CLI 阻塞到终态, 一个回合换一个结果 |
| **自检与自更新** | 取回 Skill 完整层、比对版本、报告为什么连不上. 判断「是网络、token 还是版本问题」需要把三件事放在一起看, 让模型逐条试反而更慢 |

反过来, 以下事情**不构成理由**, 因此 CLI 不做: 为每个工具生成子命令 (目录端点已给出参数, 再生成一遍就是第二份契约); 渲染表格给模型看 (模型读 JSON 更准); 校验入参 (端点已经校验); 用退出码表达业务错误 (200 里的 `error` 才是权威).

### 形态: Go 单一静态二进制

CLI 用 Go 写, 交叉编译成各平台的单一静态二进制. 这一条同时解决三件事: 不依赖用户本机任何运行时; 一次构建产出全部平台; 体积数 MB.

| 决策 | 选择 | 理由 |
|------|------|------|
| 语言 | Go | 标准库足够 (net/http, encoding/json, os, path/filepath), 无第三方依赖 |
| 构建 | 一个 CI job 交叉编译五个目标 | linux/darwin × amd64/arm64 + windows/amd64 |
| 依赖 | 仅标准库 | 空 `go.mod` 依赖列表; 升级不牵动供应链 |
| 复用 | 与服务器零共享代码 | CLI 不知道任何工具名, 本来就没有可共享的逻辑 |
| 版本注入 | 构建期 `-ldflags -X` 写入版本 | `doctor` 的版本比对依赖它, 不读运行时文件 |

### 分发: GitHub Releases

二进制与实例解耦. 实例、桌面 app、镜像都**不携带**它; 智能体按引导指引自己从 GitHub Releases 下载.

| 环节 | 做法 |
|------|------|
| 发布 | 打 tag 时由 CI 交叉编译并挂到该 Release, 产物名 `amane-{os}-{arch}` (Windows 加 `.exe`) |
| 获取 | 智能体判断平台后下载 `releases/latest/download/amane-{os}-{arch}` |
| 校验 | Release 附 `SHA256SUMS`, 下载后校验 |
| 源码 | `go build ./cli/cmd/amane` |

**为什么不再随实例走**: 二进制与实例版本本来就不必绑定 —— 协议只有三个端点, 变化极少, `doctor` 会报告差异而不是拒绝工作. 一旦解耦, 桌面壳不必打包、镜像不必变大、构建顺序不必排序, 三者都简单了.

**代价与对策**: 版本可能错配. `doctor` 报告 CLI 版本与实例版本, 不一致时给出提示但不阻断; `amane upgrade` 可拉取指定版本.

**macOS 的注意点**: 经浏览器下载的二进制会被 Gatekeeper 拦下; 用 `curl` 下载则不带隔离属性, 可以直接运行. 因此引导指引里明确要求用 `curl`, 不给「点击下载」的网页链接.

### 安装位置与调用方式

安装位置由智能体与用户商量决定, 不是固定值. 引导指引要求它**先问再装**, 并给出默认建议:

| 选项 | 说明 |
|------|------|
| 用户已有的可执行目录 | 若该目录在 `PATH` 上, 装完即可直接调用 |
| `~/.local/bin/` (Windows 为 `%LOCALAPPDATA%\Amane\bin\`) | 默认建议; 不在 `PATH` 上时用绝对路径调用 |
| 用户指定的其它位置 | 照办, 并记下绝对路径 |

**不允许智能体擅自修改 shell 配置**. 需要加入 `PATH` 时, 它应给出要追加的那一行, 经用户同意后再写.

智能体拿不到用户的交互式 shell 环境: 它执行的是非登录 shell, `~/.local/bin` 常常不在 `PATH` 里; 有些环境甚至没有 `PATH` 的概念. 因此安装完成后, **绝对路径要写进 Skill**, 调用顺序是:

| 顺序 | 方式 |
|------|------|
| 1 | Skill 里记录的绝对路径 |
| 2 | `command -v amane` (仅当确认在 `PATH` 上) |
| 3 | `curl` 直连端点 (等价路径, token 经 `curl -K` 配置文件读取) |

### 鉴权

CLI 首次运行会解析实例地址与 token, 分两种情况:

| 场景 | 行为 |
|------|------|
| 本机运行实例 | 自动从实例数据目录读取 token 文件, 用户零操作 |
| 跨机 | 需要用户手动登录一次: `amane login --server <地址>`, 由 CLI 提示用户粘贴 token (标准输入, 不进历史) |

token 只在 CLI 进程内与 0600 配置文件里出现, **从不进入模型上下文**. 引导指引明确要求智能体不得代用户粘贴 token, 也不得读取或回显它.

### 升级

`amane upgrade` 从 GitHub Releases 取新版本替换自身. 二进制不属于任何签名过的包, 替换不会破坏签名.

### 自检

`amane doctor [--json]` 报告四件事: CLI 自身路径、版本与平台, 实例可达性与版本, token 是否有效, 已安装 Skill 的版本是否与实例一致. Skill 要求智能体在首次使用或遇到连接类错误时先跑它, 把「为什么调不通」变成一条可读结论, 而不是反复试探.

### 可达性

智能体只要**网络可达实例且持有 token** 就能使用, 与它是否与服务同机无关. 可达性由实例的监听地址决定, 不由本方案决定:

| 部署 | 监听 | 谁能连 |
|------|------|--------|
| 桌面 app | 默认 `127.0.0.1` | 只有同机进程. 要跨机须改监听地址或加反向代理 |
| Docker / 服务器 | 默认 `0.0.0.0` 并映射端口 | 局域网内任何机器; 跨公网经反向代理或隧道 |

因此「云端沙箱里的智能体用不了」只在实例绑回环时成立, 不是接口的限制. 跨机使用时建议走 HTTPS: token 是唯一凭据, 明文链路会泄露它.

与可达性相邻、但**不是同一件事**的是文件系统可达: 读日志、配置、DB 文件要求智能体与服务在同一台机器上. 跨机时这部分能力退回接口与记录导出, 见「自服务指引」. 两件事要分开判断, 不要因为网络能连就以为能读文件.

### 命令结构

命令表**不随工具变化**. CLI 不知道任何工具名, 只把端点当作目标:

| 命令 | 作用 |
|------|------|
| `catalog` | 打印目录 (工具、参数、库结构、运行时路径) |
| `call <tool> [@file\|JSON]` | 派发一次工具调用, 入参来自文件、标准输入或字面量 |
| `wait <task-id>` | 轮询任务到终态并返回结果, 替代调用方自己的循环 |
| `api <path>` | 直通 REST, **仅 GET**, 覆盖尚未工具化的读面 |
| `doctor` | 自检: CLI 路径与版本、实例可达性、token、Skill 版本 |
| `upgrade` | 从实例取回同平台的新二进制替换自身, 保持与实例同版本 |
| `login` / `config` | 写入实例地址与 token, 管理多实例 profile |
| `skill install` / `show` | 写入智能体 Skill 目录 / 打印完整层到标准输出 |

由此得到一个直接的好处: **新增工具不需要改 CLI**, 也就不存在 CLI 与目录两份契约漂移的问题. CLI 只在端点形状变化时才需要跟着改, 而那是真正的破坏性变更.

`api` 只允许 GET 是刻意的: 所有写操作必须经过工具层, 才能进入审计. 日志、配置、文件浏览不进命令表 — 同机时由智能体直接读文件, 远端时经 `api` 取已有的记录导出端点.

破坏性工具不加确认开关: CLI 不做「是否继续」的交互提示, 也不接受 `--yes`. 需要用户同意是对话层的事 (见 Skill 的审批礼仪), CLI 只是执行器; 在 CLI 里加一道按键确认既拦不住脚本, 又会让智能体绕过提示, 反而制造「已确认」的假象.

### 输出与退出码

输出即端点响应的 JSON 原文, 不做表格渲染: 调用方是模型或脚本, JSON 最省事也最准确. `--pretty` 供人读.

| 退出码 | 含义 |
|--------|------|
| 0 | 请求完成. 工具返回的 `error` 仍在 0 里, 看响应体 |
| 2 | 用法错误 |
| 3 | 连接失败或鉴权失败 |

退出码只区分「有没有拿到响应」, 不重复表达业务结果 — 业务结果只有一个权威位置, 就是响应体. 数据写 stdout, 诊断信息写 stderr.

### 配置

配置文件位于用户配置目录, 权限 0600, 按 profile 保存实例地址与 token. token 取值优先级: profile → 环境变量 → 本机数据目录的 token 文件 (仅同机可用).

**不接受命令行参数传 token**, 也不回显: 前者会进 shell 历史与 `ps`, 后者会进模型上下文. 唯一的写入途径是 `login` 从标准输入读取. 指向非回环地址且为明文 HTTP 时给出警告, 不阻断: 局域网自托管是主要形态.

## Skill

### 内容

| 文件 | 内容 | 来源 |
|------|------|------|
| `SKILL.md` | 触发条件、基本工作方式、审批礼仪 | 手写 |
| `reference.md` | 工具清单、参数、返回形状、错误处理, 以及 CLI 与裸 curl 两种调用式 | 由目录生成 |
| `self-service.md` | 日志、配置、数据库、源码的位置与读法 | 由目录的运行时事实生成 |
| `workflows.md` | 常见工作流: 批量重刮、失败任务排查、演员合并、分类规则整理、订阅源历史批处理、定时报告 | 手写 |

审批礼仪是 Skill 的核心约束, 因为服务端不再设闸门: 执行破坏性操作前必须先向用户复述影响面 (改什么、涉及多少条、能否撤销) 并取得明确同意, 得到答复后才调用. 章节逐项点名这些操作 (删除番号条目 / 演员别名 / 分类 / 媒体库 / 订阅源 / 定时任务, 合并分类与条目, 批量修改, 放宽超时执行慢查询), 并说明「用户未答复或答复含糊时不执行」. 另有一条测试断言被点名的工具都存在于目录中, 防止改名后指引失效.

### 自服务指引

Skill 必须让智能体先意识到「很多事我自己就能做」, 再决定是否调用接口. 该章节按实例给出的路径描述四类位置:

| 对象 | 指引 |
|------|------|
| 任务日志 | 应用日志与请求日志在日志目录; 单任务日志、配置快照、站点结果、出站 HTTP 记录在 `tasks/task-{id}/` 下, 失败排查从这里读, 不需要接口 |
| 配置 | 配置文件路径与决定路径的环境变量; 密钥字段在其中, 读取时不得回显 |
| 数据库 | DB 文件路径. 可直接以只读方式查询, 但优先经 `sql_explore` 工具 — 它复用沙箱、超时与查询预设 |
| 源码与文档 | 安装目录或仓库; 遇到语义不确定时读实现与开发文档, 而不是猜测接口行为 |

远端实例无法访问服务端文件系统时, 日志改用已有的记录导出端点 (整包 zip). 该分支也写进本章节, 不额外做接口.

生成这两类内容时按**网络可达**与**文件系统可达**分别判断: 前者看实例地址, 后者看数据目录是否在本机. 二者可同时成立 (同机), 也可只成立前者 (跨机), 不存在只成立后者的情况.

### 领域规则复用

助理的系统提示里已经有一份领域说明书: 表结构与连接键、交付语义、任务入队与类型、只读 SQL 的用法. 这份内容对外部智能体同样成立. 实现时把它拆成共享文本块, 助理提示与 Skill 参考页从同一份来源生成, 避免两套规则各自演化.

### 分发: 引导层与完整层

Skill 分两层, 职责不同, 更新节奏也不同.

| 层 | 内容 | 从哪来 | 何时更新 |
|----|------|--------|---------|
| **引导层** | 接入指引: 装 CLI、鉴权、装 Skill、约束 | `GET /public/agent`, 固定文本 | 随版本发布, 用户无需搬运 |
| **完整层** | 工具清单、参数、返回形状、自服务指引、工作流 | `amane skill install` 从实例写入 | 实例升级后重跑 |

引导层不是文件, 而是一次 `curl` 的结果 —— 因此它没有「安装」这一步, 也不存在过期的副本. 它只负责把智能体送到「CLI 已装、已鉴权、Skill 已装」这个状态, 不承载工具清单与业务规则.

完整层由实例生成, 因此天然与实例版本一致: `skill install` 从 `GET /api/tools` 取数据渲染, 写入时带上实例版本号; `doctor` 比对, 不一致时提示重跑.

完整层同时入库一份生成物, 并有测试断言其与目录一致, 防止漂移.

对没有 Skill 机制、只能读固定文件的客户端: 引导层照样能 `curl`, 完整层可以打印到标准输出后手工贴入对话. 功能不减, 只是每次会话要多贴一次.

## 鉴权与数据保护

### 判断

本期不引入细粒度 API key. 依据:

- 现有 token 已经是完整控制权 (REST 全量可达), 新增接口只是把已有能力换一种形状, 不扩大权限面.
- 唯一免鉴权的端点是引导端点, 它只回固定文本, 不含任何实例数据 —— 公开它不增加泄露面.
- 单用户自托管, 持有 token 即视为用户本人; 同机能读数据目录的进程早已在信任边界内.
- 细粒度令牌需要令牌管理、权限模型、前端授权界面与逐接口校验, 成本远高于当前收益.

### 本期要做的三件事

1. **审计**: 派发日志记录工具、结果类别、入参摘要与请求 id, 破坏性操作可追溯. 服务端没有闸门, 这是唯一的事后手段.
2. **token 保管**: CLI 配置文件 0600, token 不进命令行回显、不进日志、不进 URL; 明文传输告警.
3. **边界声明**: Skill 与用户文档明确「持有 token 等同本人」, 不把接口包装成可安全分享的协作通道, 也不暗示存在服务端确认.

### 将来的扩展点

若需要给第三方智能体受限权限, 改动只落在派发层: 目录里为每个工具标注变更等级 (只读 / 写入 / 破坏性), 令牌携带允许的等级集合, 派发前校验. 工具层与 CLI 不受影响.

审批硬约束与它是两件事, 不要合并设计: 令牌 scope 限制「能调用什么」, 审批限制「这一次要不要人点头」. 后者见「审批」一节, 需要浏览器确认页与待批记录, 单独立项.

### 新增读面的边界

只读 SQL 会暴露整库. 库内没有凭据 (站点密钥在配置文件中, 不在 DB), 因此新增读面的实际增量很小. 若后续认为内部表 (会话、预设) 不应外露, 可在沙箱层加表级排除, 不需要改接口.

## 覆盖与缺口

| 能力 | 外部接口 |
|------|---------|
| 番号条目、演员、分类、媒体库、订阅源、定时任务、任务队列的写操作 | 工具层全量可用 |
| 任意只读查询 | 只读 SQL |
| 面向界面的结果交付 | 查询预设 |
| 任务日志、配置、文件、源码 | 指引: 直接读文件; 远端经记录导出端点 |
| 配置、来源插件、评论、字段锁、手动裁切 | **不开放**: 未经工具层, 没有领域校验与审计 |
| 文件浏览 | 指引: 本地直接读; 远端经 `api` 直通 |
| 接入指引 | `GET /public/agent`, 免鉴权, 固定文本 |

写操作只经工具层的规则带来一个明确后果: 尚未工具化的写能力对外不可用. 需要时按「加工具」而不是「放开 REST 写」处理.

读面的判断标准不是「能不能做接口」, 而是「外部智能体能否自行完成」. 能自行完成的只写指引, 于是接口面保持在领域语义这一层, 不随功能增长而膨胀.

## 用户旅程

从「刚装好」到「在 [CC] 里能用」的完整路径. 本节是设计的验收标准: **用户只需要给出一个 URL**, 其余全部由智能体按引导指引自行完成; 任何一步要求用户理解接口细节, 都说明设计有问题.

### 起点: README 的一行

README「安装」段落末尾加一行入口, 指向 `docs/user/agent.md`. 措辞只讲结果, 不讲机制: 用你自己的 AI 智能体管理 Amane.

### 用户实际要做的三步

| 步 | 用户动作 | 说明 |
|----|---------|------|
| 1 | 打开 Web UI 的「连接智能体」页 | 页面只显示一个地址, 例如 `http://127.0.0.1:8000/public/agent`, 附复制按钮 |
| 2 | 把地址粘给 [CC] | 一句话即可, 不需要额外解释 |
| 3 | 回答智能体的提问 | 装到哪里、要不要加 `PATH`、跨机时粘贴一次 token、Skill 装到哪个目录 |

之后不再需要用户操作. 前两步是「给一个 URL」, 第三步是智能体按引导指引逐项征求同意 —— 这正是把「问」写进引导文本的原因.

### 页面要显示的

「连接智能体」页只有一个地址与一段三行说明 (它会让你做什么、会问你什么、token 不会经过对话). 不显示 token, 不显示数据目录, 不显示版本 —— 这些都不该出现在一个用来复制的字符串旁边.

### 用户粘过去的那句话

可以就是 URL 本身, 也可以是一句「用这个地址接入我的 Amane: <URL>」. 两者都行, 因为全部指引在服务端返回的文本里.

### 服务端返回什么

`GET /public/agent` 的固定文本, 结构见「引导端点」. 它由智能体自行 `curl`, 因此这段文本是整个接入过程真正的说明书. 关键要求:

| 要求 | 原因 |
|------|------|
| 不含 token 与任何本机路径 | 端点公开, 且文本可能进入模型上下文 |
| 明确「先问再装」 | 安装位置、`PATH` 修改、Skill 目录都必须用户同意 |
| 说明两种鉴权路径 | 同机自动发现, 跨机手动登录一次 —— 智能体据此判断要不要打断用户 |
| 给出结束条件 | 跑通 `doctor` 才算完成, 避免半成品状态 |

### 智能体侧发生什么

1. `curl <URL>` 取得指引, 从 URL 推断实例地址.
2. 判断平台, 从 GitHub Releases 下载二进制, 校验 `SHA256SUMS`.
3. 询问安装位置与是否加入 `PATH`, 按答复安装.
4. 鉴权: 同机直接可用; 跨机引导用户执行 `amane login` 并自行粘贴 token.
5. `amane doctor` 全部通过.
6. 询问 Skill 安装目录, 执行 `amane skill install`, 读完整说明.
7. 此后所有操作经由 CLI.

### 失败分支

| 现象 | 用户做什么 |
|------|-----------|
| 智能体取不到引导文本 | 确认实例在运行, 地址与端口正确 |
| 下载失败 | 手动从 Release 页取对应产物, 或让智能体改用 `curl` 重试 |
| macOS 提示无法验证开发者 | 产物是经浏览器下载的, 带了隔离属性. 改用 `curl` 重新下载 |
| `doctor` 报鉴权失败 | 在自己的终端执行 `amane login`, 从 Web UI 复制 token 粘贴 (标准输入, 不进历史) |
| `doctor` 报版本不一致 | 提示但不阻断; 需要时 `amane upgrade` |
| 智能体不能执行 shell | 前提不满足. 文档页明确写清: 需要能跑命令的智能体 |

### 之后

- **日常使用**: 用户直接说人话, 智能体自己决定调哪个工具. 用户不再看到命令.
- **实例升级**: Skill 完整层由实例生成, 版本不一致时 `doctor` 提示, 重跑 `amane skill install` 即可.
- **CLI 升级**: 与实例无关, `amane upgrade` 拉最新版.
- **多实例**: 一个 profile 一个地址, CLI 用 `--profile` 切换.

## 实施阶段

| 阶段 | 内容 | 规模 |
|------|------|------|
| P0 | 引导端点、工具目录 (含运行时路径) 与派发、上下文共用、会话归属改动、破坏性工具描述补影响面、审计、接口测试 | 2 天 |
| P1 | Go CLI (`catalog` / `call` / `wait` / `api` / `doctor` / `login` / `upgrade` / `skill`)、交叉编译 CI job 与 Release 附件 (`SHA256SUMS`) | 3 天 |
| P2 | Skill 完整层四个文件与生成脚本、引导文本定稿、防漂移测试、Web UI「连接智能体」页、`docs/user/agent.md` 与 README 入口 | 2 天 |
| P3 | 可选: 审批硬约束 (待批记录 + 浏览器确认页)、工具变更等级与令牌 scope、MCP 映射 | 按需 |

P0 完成即可用 `curl` 验证全部能力; P1 之后可交付给终端用户试用; P2 之后新用户按「用户旅程」走一遍就能在 [CC] 里用, 才算完整产品形态.

## 测试

- 引导端点: 免鉴权可访问; 响应在两次请求间逐字相同; 不含 token、路径、版本等任何实例数据; 未命中 SPA fallback.
- 目录: 工具数量与名字的完整快照, 参数 Schema 非空, 无重名, 运行时路径块与配置一致.
- 派发: 未知工具、参数校验失败、工具 `error` 透传、未配置模型时可用.
- 无闸门: 破坏性工具经派发直接执行 (与助理路径的审批中断不冲突), 且审计日志留下一条记录.
- 会话归属: 外部交付的预设无会话且已保留; 探查视图不进预设列表.
- CLI: 子进程级测试 (以假服务端驱动), 覆盖 `call` 的三种入参来源、`wait` 的终态判定、`api` 拒绝非 GET, 以及 token 不出现在输出中.
- 调用链: 在 `PATH` 不含安装目录的干净环境下, 按 Skill 记录的绝对路径可直接运行.
- 依赖基线: `go.mod` 无第三方依赖.
- 分发: Release 附件覆盖五个平台且校验和匹配; 二进制在干净容器中可直接运行 (无动态库依赖).
- Skill: 完整层与目录一致; 自服务章节的路径取自实例而非硬编码; 审批礼仪点名的工具都在目录中; 引导层不含任何会随版本变化的内容.
- 用户旅程: 按「用户旅程」一节在全新环境走一遍, 中途不查阅源码与接口文档即可到达「在智能体里完成一次真实查询」.
- 端到端: 起服务 → 建库 → SQL 探查 → 交付 → 入队 → 等终态 → 读日志目录.

## 风险

| 风险 | 处理 |
|------|------|
| 取用方式依赖框架非公开面 | 收敛到单一适配模块; 全量目录测试在升级时立即失败 |
| 工具名成为对外契约 | 接受: 这正是单一事实源的目的; 改名按破坏性变更处理, 目录端点使客户端能自描述 |
| 智能体不遵守审批礼仪, 直接执行破坏性操作 | 明确这是软约束, 服务端拦不住; 靠工具描述写清影响面、Skill 逐项点名、审计可追溯; 需要硬约束时按「审批」一节的方案单独立项 |
| 指引随版本失效 (路径或文件布局改变) | 路径由目录端点在运行时给出, Skill 生成而非手抄; 引导层刻意不含版本相关内容 |
| 智能体环境的 `PATH` 与用户 shell 不同 | 不依赖 `PATH`: 绝对路径写进 Skill, 并给出 `curl` 作为等价调用式 |
| 仓库多一种语言 | CLI 与服务器零共享代码, 边界清晰; 仅标准库, 无依赖升级负担; 构建只有一条 `go build` |
| 构建机需要 Go 工具链 | 只加在 Release 的 CI job 与开发机前置条件; 纯 Python 的 `just dev` / `just test` 不受影响 |
| macOS Gatekeeper 拦截 | 引导指引明确要求用 `curl` 下载, 不给浏览器下载链接 |
| 智能体没有 skill 机制 | 引导层可退化为一段贴进对话的说明; 完整层支持打印成文本. 功能仍可用, 代价是每次会话重新贴一次 |
| 「连接智能体」页排期靠后 | 引导地址可由用户自己拼 (实例地址 + `/public/agent`), 文档页写出规则即可; 页面只是把这一步变成一次点击 |
| 助理与外部接口的行为漂移 | 工具层改造需同时跑助理测试与派发测试 |

## 未决问题

- 配置与来源插件的只读查询是否开放 (读安全, 写危险), 需要与「不开放」的边界重新对齐.
- 是否需要「多步脚本」模式 (一次读取多行命令), 还是交给智能体逐条调用.
- 是否把查询预设的 `persisted` 默认值改为可配置, 让外部交付默认进入预设列表还是仅按 id 取用.
- 审批硬约束何时立项: 触发条件是「有用户把接口暴露给不完全信任的智能体」, 在那之前软约束足够.
