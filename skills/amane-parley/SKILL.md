# 双人讨论协议

两个 Agent 各持一个角色, 通过落盘文件轮流发言. 被评审的产物在讨论开始前就已存在, 协议不承载它,
只承载双方的回合.

## 角色

**主理人** (`author`) — 负有责任的产出方.

- 讨论设计方案时: 方案由主理人预先写好, 讨论结束后由主理人负责实现.
- 评审 PR 时: 该 PR 的实现者.
- 可以修改仓库文件、提交与推送分支.

**批评家** (`critic`) — 只做批评, 不执行任何其他动作.

- 指出缺陷、质疑假设、给出可执行的改进建议.
- **不得**修改仓库文件, **不得**执行任何有写操作的 git 命令, **不得**合并 PR.
- 可以读取任意文件, 可以运行测试与只读检查, 用取得的结果作为批评依据.

## 产物

被评审的产物在讨论开始前已经存在, 通常不在工作目录内:

| 场景 | 产物 |
| --- | --- |
| PR review | 分支上的代码 |
| 设计方案 | 项目文档目录下的方案文件, 例如 `docs/plan/xxx.md` |

产物位置由 `init --artifact` 声明. 批评家从工具输出中读取该字段, 不需要另外告知.

## 工作目录与文件约定

主题目录位于 `<仓库根>/.parley/<topic>/`. 仓库根等于工作目录的上两级目录.

```
.parley/<topic>/
  manifest.json              由 init 创建, 记录 subject、artifact 与轮次上限
  .staging/                  暂存区, 对方的等待逻辑不进入此目录
  01-critic.md               批评家第 1 轮评审
  01-author.md               主理人第 1 轮回应
  02-critic.md               批评家第 2 轮评审
```

一轮由一次批评家评审与一次主理人回应组成, 因此**批评家先落盘**, 主理人不存在独立的提案文件.

**不要自行构造文件名.** 暂存路径由 `next` 给出, 契约文件名由工具推导. 直接向工作目录写
`01-critic.md` 会绕过发布校验, 导致对方读到写了一半的内容.

## 调用

工具位于本 skill 目录, 只依赖 Python 标准库:

```
uv run skills/amane-parley/parley.py <子命令> [选项]
```

子命令为 `init`、`next`、`publish`、`wait`、`status`. 全部输出为单个 JSON 信封:

| 字段 | 用途 |
| --- | --- |
| `ok` | 唯一的成败判据 |
| `message` | 自然语言说明. 只读这一项即可决定下一步 |
| `data` | 结构化字段, 路径与产物一律从这里取 |
| `error` | 失败时为稳定的错误标识, 成功时为 `null` |

**进程退出状态恒为 0**, 不要依据退出状态判断成败. 需要分支时匹配 `error`, 其取值为
`usage_error`、`no_workspace`、`invalid_staging`、`staging_missing`、`not_your_turn`、
`round_limit`、`no_pending_turn`、`already_published`、`timeout`、`interrupted`、
`internal_error`.

## 发起讨论

主理人先确保产物已经产出, 然后执行:

```
parley init <topic> --subject "<一句话说明讨论什么>" --artifact "<被评审对象的位置>"
```

两个选项均必填. 主题目录默认位于仓库根的 `.parley/` 下, 通常不必指定 `--root`.

`init` 之后讨论从批评家第 1 轮开始, 主理人运行 `wait --for critic` 等待其评审.

批评家不执行 `init`, 只需要工作目录路径. 它从 `next` 的输出中取得 `subject` 与 `artifact`.

## 操作循环

主理人与批评家执行同一个循环, 仅角色取值不同.

```
1. parley next --dir <工作目录> --role <本方角色>
   从 data.staging_path 取得暂存路径
   从 data.peer_path 取得需要阅读的对方回合
   批评家第 1 轮的 peer_path 为 null, 此时读 data.artifact
2. 读取对方回合与产物
3. 把本轮内容写入 staging_path
4. parley publish --file <staging_path>
5. parley wait --dir <工作目录> --for <对方角色>
   从 data.path 取得对方本轮文件
6. 读到对方表示结束的回合, 或自己判断讨论可以结束时, 停止; 否则回到第 1 步
```

第 1 步返回 `not_your_turn` 时说明尚未轮到本方, 应先执行第 5 步等待对方.

## 回合内容

回合文件为自由格式的 Markdown, 工具不解析也不校验正文. 内容写给对方看, 目标是让对方能据此
判断与修改产物.

## 硬性约束

- 已发布的回合文件不可修改, 也不可覆盖. 需要修正时发布下一轮.
- 不得直接向工作目录写入契约文件名, 必须经由 `next` 与 `publish`.
- 批评家不得修改仓库文件、执行有写操作的 git 命令、或合并 PR.

## 终止

任一方判断讨论可以结束时, 发布本轮回合并说明结论, 然后停止, 不再等待. 对方读到该回合后同样
停止.

发布动作本身就是释放: 对方的等待在本轮落盘时已经返回. 因此先结束的一方不会把对方挂在阻塞上,
也不需要额外一轮收尾.

常见情形:

- 批评家没有更多意见时, 在自己的回合中说明, 然后停止. 主理人读到后把最终结论写入 PR 正文或
  方案文档.
- 主理人认为已经足够时, 在回应中说明并停止. 批评家读到后停止, 不再发起新一轮评审.
- `next` 或 `wait` 返回 `round_limit`. 主理人在最后一轮回应中写明未收敛的分歧.

故障情形:

- `wait` 返回 `timeout` 或 `interrupted`, 或对方进程已不存在. 主理人汇总双方立场后自行输出
  结论, 并把情况报告给用户.

批评家从不输出最终结论.
